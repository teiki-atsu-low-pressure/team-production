# 開発フロー（Issue 駆動 × develop ブランチ運用）

## 全体の流れ

1. **Issue を立てる**（`feat` / `fix` / `change` は必須。それ以外は任意。[Issue のルール](#issue-のルール)を参照）
2. 着手するときに、Issue の **Assignees（担当者）に自分を入れる**（[用語](#用語)を参照。Issue がない作業は飛ばしてよい）
3. 最新の `develop` から作業ブランチを切る（別の作業ブランチにいるまま切らないこと）
   ```
   git switch develop
   git pull
   git switch -c <ブランチ名>
   ```
4. 作業ブランチでコミットを積む
5. `develop` 向けに PR を作成する（本文に `Closes #<Issue番号>` を書く）
6. 1 人以上の承認（Approve）をもらって `develop` にマージする
7. マージ後、GitHub 上のブランチは自動で削除される（Issue も `Closes` により自動で閉じる）。ローカルは各自で掃除する：
   ```
   git switch develop
   git pull
   git fetch --prune
   git branch -d <ブランチ名>
   ```
   - マージ後に追加の修正が必要になったら、同じブランチは使わず `develop` から新しいブランチを切る

## 作業中に `develop` が更新されたとき

自分のブランチに最新の `develop` を取り込む：

```
git switch develop
git pull
git switch <自分のブランチ>
git merge develop
```

- 取り込みは `merge` で行う（`rebase` は使わない。push 済みブランチの rebase には force push が必要になり、事故のもとになるため）
- PR を出す前と、PR でコンフリクトが表示されたときには必ず取り込む

### コンフリクトが起きたら

1. VS Code でコンフリクトしたファイルを開き、どちらの変更を残すか選ぶ（「Resolve in Merge Editor」ボタンを使うとわかりやすい）
2. 解決したら、コミットしてマージを完了する
   ```
   git add <ファイル名>
   git commit
   ```
3. わからなくなったら、`git merge --abort` でマージ前の状態に戻せる

- 相手の変更を消してよいか判断できないときは、自分で決めずに Discord で相手に相談する（誰が変更したかは、GitHub のファイル画面の「Blame」や `git log -p <ファイル名>` で確認できる）

## 用語

| 用語 | 意味 | 設定する場所 |
|---|---|---|
| **Assignees（担当者）** | その Issue / PR の作業を担当する人 | Issue / PR 画面の右側「Assignees」 |
| **Reviewers（レビュアー）** | PR をレビューして承認（Approve）する人。担当者とは別の人を指定する | PR 画面の右側「Reviewers」 |

## Issue のルール

| 作業の種類 | Issue |
|---|---|
| `feat` / `fix` / `change` | **必須** |
| `refactor` / `docs` / `test` / `chore` | 任意（小さな作業なら Issue なしでよい） |

- Issue は [テンプレート](../.github/ISSUE_TEMPLATE/) を使って作成する
- 着手前に Assignees を確認し、他の人が担当中のものには手を出さない
- タスクは **GitHub Issue に一本化** する。Discord は相談・連絡用とし、Discord で決まったタスクは Issue に起こす

### 立てるときと着手するとき

| タイミング | ルール |
|---|---|
| **立てるとき** | ざっくりでよい。タイトルと一言だけでもよい（例:「DB の接続なんか悪くない？」）。気づいたらすぐ立てる |
| **着手するとき**（Assignees に自分を入れるとき） | 担当者が「目的」と「完了条件」を書き足す。大きすぎたら分割する。ラベルが内容と合っていなければ付け替える |

### タイトルとラベル

- タイトルには中身だけを書く（`[feat]` などの接頭辞は付けない）
- 種類はラベルで区別する。テンプレートを選ぶと自動で付く

| ラベル | 種類 |
|---|---|
| `enhancement` | 機能追加・仕様変更 |
| `bug` | バグ |
| `question` | 相談・気づき（まだ整理できていないもの） |

- 相談（`question`）から作業になった Issue は、着手する人がラベルを `enhancement` か `bug` に付け替える

### 粒度の目安

- 1 Issue は **1〜3 日で終わる大きさ** にする。それより大きければ、着手時に Issue を分割する
- 1 Issue = 1 PR

## PR の書き方

PR は、あとから「なぜこうなったのか」を追うための記録なので、Issue よりしっかり書く。

### タイトル

- **コミットメッセージと同じ形式** で書く（例: `feat: Google OAuth ログインを追加 #12`）
  - PR 一覧で種類と内容がひと目でわかるようにするため。PR タイトルはマージコミットの本文にも残る
- リリース PR（`develop` → `main`）のタイトルは「[リリース](#リリースdevelop--main)」を参照

### 本文

[PR テンプレート](../.github/pull_request_template.md) の各欄を埋める。

- **なぜ変更したか**：背景・目的。「何を」だけでなく「なぜ」を必ず書く
- **何を変更したか**：変更点を箇条書きで書く
- **確認方法**：レビュアーが動作を確かめる手順を書く
- **レビューで特に見てほしい点**：自信がない所、判断に迷った所があれば書く（任意）
- **スクリーンショット**：画面の変更がある場合に貼る

PR が大きくなるとレビューが大変になり、放置されやすい。大きくなりそうなら Issue を分割するか、Draft PR で早めに相談する。

## レビューのルール

### PR を出す人

- PR 作成時に Reviewers を 1 人以上指定する（迷ったら Discord で依頼する）
- 反応がなければ、Discord で催促したり、別の人に頼み直したりしてよい
- 指摘を受けたら、対応して push し、コメントに返信したうえで、PR 画面の Reviewers 横の 🔄（**Re-request review**）を押して再レビューを依頼する
- Approve をもらった後に追加で変更を push した場合は、レビュアーに一声かける（追加の push では Approve は取り消されないため）
- 承認をもらったら、**PR を出した本人がマージする**

### レビューする人

- 依頼に気づいたら、なるべく早く見る
- すぐに見られないときは、黙って放置せず Discord で一言伝える（「明日見ます」「他の人お願い」など）
- 見るポイント
  - Issue の完了条件を満たしているか
  - 手元で動かして、動作に問題がないか
  - ブランチ名・コミットメッセージがルールに沿っているか
  - パスワードや API キーなどが含まれていないか
- 結果は以下のどれかで返す
  - **Approve**：問題なし
  - **Request changes**：直さないとマージできない点がある
  - **Comment**：質問や提案だけ（マージは止めない）

## Draft PR

- 作業途中でも、相談したいときや進み具合を見せたいときは **Draft PR** を出してよい（PR 作成画面の「Create pull request」横の ▼ から「Create draft pull request」を選ぶ）
- 完成したら「Ready for review」を押して、Reviewers を指定する

# ブランチ戦略

## ブランチの種類

| ブランチ名 | 用途 |
|---|---|
| `main` | 安定版。発表・デモで使う状態を保つ。`develop` からのリリース PR でのみ更新する |
| `develop` | 開発の統合先（デフォルトブランチ）。作業ブランチはここから切り、ここへ PR を出す |
| `<type>/<Issue番号>-<説明>` | Issue がある作業ブランチ |
| `<type>/<説明>` | Issue がない作業ブランチ |

`<type>` は[コミットメッセージの type 一覧](#type-一覧)と同じものを使い、**その PR の主な目的** で決める。
ブランチ内のコミットの type は一致しなくてよい（例: `feat/12-google-oauth` の中に `test:` や `docs:` のコミットがあってよい）。

## リリース（`develop` → `main`）

- タイミング：発表・デモの前、または機能のまとまりができたとき
- 担当：**発表・デモを担当する人** がリリース PR を作る（いなければ Discord で決める）
- `main` でバグが見つかった場合も、通常どおり `develop` で修正し、次のリリースで `main` に反映する（`hotfix` ブランチは作らない）

### 手順

1. `develop` → `main` の PR を作成する
   - タイトル例：`中間発表版のリリース`
   - 本文には次の 2 つを書く。PR テンプレートのうち該当しない欄（`Closes #` など）は消してよい
     - 前回のリリースから入った PR の一覧
     - 発表・デモで使う機能が動くことを確認したこと
2. レビュアー 2 人は、`develop` を手元で動かし、発表・デモの流れを一通り試す
3. 2 人以上の承認をもらってマージする
4. GitHub の **Releases** でタグを付けて残す
   1. リポジトリ画面右側の「Releases」→「Draft a new release」を開く
   2. 「Choose a tag」に新しいタグ名を入力して作成する。Target は `main` にする
   3. タイトルを入力し、「Generate release notes」を押す（含まれる PR の一覧が自動で入る）
   4. 「Publish release」を押す

### タグの付け方

| タグ | 使う場面 | タイトル例 |
|---|---|---|
| `v0.1`, `v0.2`, … | 中間発表・デモなど、途中のリリース | `v0.1 中間発表版` |
| `v1.0` | 最終発表 | `v1.0 最終発表版` |

- タグ名は英数字のみにする（日本語はタイトルに書く）
- 過去のリリースの状態は、`git switch --detach v0.1` で見られる（見終わったら `git switch develop` で戻る）

## 命名規則

- 英小文字・数字・ハイフンのみ使用する（`<説明>` は kebab-case）
- 例:
  - `feat/12-google-oauth`
  - `fix/34-cache-race-condition`
  - `docs/update-readme`（Issue なし）

## ルール

- `main` / `develop` への直接プッシュは禁止
- 必要な承認（Approve）の数（自分の PR は自分で承認できない）
  - `develop` への PR：1 人以上
  - `main` への PR：2 人以上
- ※ 上記と `main` / `develop` の削除・force push 禁止は、GitHub の Ruleset（`protect-main` / `protect-develop`）で強制されている
- マージ方法は **Merge commit のみ**（Squash / Rebase は GitHub の設定で無効化済み）
  - PR 内のコミットはすべて履歴に残るので、PR を出す前に意味のないコミット（`wip`、`修正` だけ等）がないか見直す
  - PR 単位の流れだけ見たいときは `git log --first-parent develop` を使う
- 1 ブランチ = 1 目的（複数の変更を混在させない）
- 個人用の作業ブランチ（例: `daiki-work`）は作らない

# コミットメッセージ規約

[Conventional Commits](https://www.conventionalcommits.org/ja/v1.0.0/) をベースにする。絵文字は付けない。

## 基本フォーマット

```
<type>[(scope)]: <説明> [#Issue番号]

[本文（任意）]
```

## type 一覧

| type | 用途 |
|---|---|
| `feat` | 新機能の追加 |
| `fix` | バグ修正 |
| `change` | 既存機能の仕様変更 |
| `refactor` | 動作を変えないコード整理（フォーマット修正を含む） |
| `docs` | ドキュメントのみの変更 |
| `test` | テストの追加・修正 |
| `chore` | 設定・ツール・依存関係・CI などの雑務 |

### `feat` / `change` / `fix` / `refactor` の見分け方

| 状況 | type |
|---|---|
| 今までなかった機能ができた | `feat` |
| すでにある機能の仕様・見た目・動きを **意図して** 変えた | `change` |
| 本来の仕様どおりに動いていなかったのを直した | `fix` |
| 動きは何も変わらず、コードだけ整理した | `refactor` |

## ルール

- `type` と `scope` は英語、`説明` と `本文` は **日本語** で書く
- `説明` は「〜を追加」「〜を修正」のように **体言止め** で簡潔に書く
- 1 行目は 50 文字程度以内を目安にする
- Issue がある場合は 1 行目の末尾に `#Issue番号` を付ける
- scope は変更範囲を括弧で示す（任意）。例: `fix(auth): トークン更新処理を修正 #34`
- 本文には「何を」ではなく「なぜ」変更したかを書く
- `git config user.email` は GitHub に登録したメールアドレスと同じにする（違うと、コミットが自分のものとして GitHub に表示されない）
- Git / GitHub が自動で作るメッセージは規約の対象外とし、そのまま使う
  - `Merge pull request #1 from ...`（PR のマージ時）
  - `Revert "..."`（`git revert` 時）

## 例

```
feat(login): Google OAuth ログインを追加 #12

既存のメール/パスワードログインと共存させる。
```

```
fix: キャッシュ無効化の競合状態を修正 #34
```

```
docs: README にセットアップ手順を追加
```

# コミットしてはいけないもの

このリポジトリは **Public**（誰でも見られる）。一度 push したものは、後で消しても履歴に残る。

- `.env` ファイル、パスワード、API キー、トークンなどの秘密情報
- 個人情報
- `node_modules` などの自動生成されるファイル（[`.gitignore`](../.gitignore) で除外する）

秘密情報を push してしまったら、すぐに Discord で報告し、そのキーを無効化（再発行）する（ファイルを消すだけでは履歴に残るため不十分）。

# AI（Claude Code など）を使うときのルール

- AI に作業させる前に、自分で作業ブランチを切っておく（AI に `main` / `develop` で直接作業させない）
- AI が push・PR 作成・Issue 操作をするときは、必ず人間が内容を確認してから実行させる
- AI が書いたコードやコミットも、自分が書いたものとして責任を持ってレビューする
- AI が関わったコミットには `Co-Authored-By:` 行を付けたままにする（どこを AI に任せたか後から振り返れるようにするため）

# ルールの変更

- このルール（RULE.md）やテンプレートを変えるときも、PR で行う
- 全員に関わるので、PR を出したら Discord で告知し、意見を募る
- GitHub の設定（Ruleset など）を変えるときは、先に RULE.md を変える PR で合意してから設定する
