# Issue・PR・レビュー

## Issue のルール

| 作業の種類 | Issue |
|---|---|
| `feat` / `fix` / `change` | **必須** |
| `refactor` / `docs` / `test` / `chore` | 任意（小さな作業なら Issue なしでよい） |

- Issue は [テンプレート](../.github/ISSUE_TEMPLATE/) を使って作成する
- 着手前に Assignees を確認し、他の人が担当中のものには手を出さない
- タスクは **GitHub Issue に一本化** する。Discord は相談・連絡用とし、Discord で決まったタスクは Issue に起こす

### 立てるときと着手するとき

| タイミング | ルール |
|---|---|
| **立てるとき** | ざっくりでよい。タイトルと一言だけでもよい（例:「DB の接続なんか悪くない？」）。気づいたらすぐ立てる |
| **着手するとき**（Assignees に自分を入れるとき） | 担当者が「目的」と「完了条件」を書き足す。大きすぎたら分割する。ラベルが内容と合っていなければ付け替える |

### タイトルとラベル

- タイトルには中身だけを書く（`[feat]` などの接頭辞は付けない）
- 種類はラベルで区別する。テンプレートを選ぶと自動で付く

| ラベル | 種類 |
|---|---|
| `enhancement` | 機能追加・仕様変更 |
| `bug` | バグ |
| `question` | 相談・気づき（まだ整理できていないもの） |

- 相談（`question`）から作業になった Issue は、着手する人がラベルを `enhancement` か `bug` に付け替える

### 粒度の目安

- 1 Issue は **1〜3 日で終わる大きさ** にする。それより大きければ、着手時に Issue を分割する
- 1 Issue = 1 PR

## PR の書き方

PR は、あとから「なぜこうなったのか」を追うための記録なので、Issue よりしっかり書く。

### タイトル

- **コミットメッセージと同じ形式** で書く（例: `feat: Google OAuth ログインを追加 #12`）
  - PR 一覧で種類と内容がひと目でわかるようにするため。PR タイトルはマージコミットの本文にも残る
- リリース PR（`develop` → `main`）のタイトルは「[リリース](branch-strategy.md#リリースdevelop--main)」を参照

### 本文

[PR テンプレート](../.github/pull_request_template.md) の各欄を埋める。

- **なぜ変更したか**：背景・目的。「何を」だけでなく「なぜ」を必ず書く
- **何を変更したか**：変更点を箇条書きで書く
- **確認方法**：レビュアーが動作を確かめる手順を書く
- **レビューで特に見てほしい点**：自信がない所、判断に迷った所があれば書く（任意）
- **スクリーンショット**：画面の変更がある場合に貼る

PR が大きくなるとレビューが大変になり、放置されやすい。大きくなりそうなら Issue を分割するか、Draft PR で早めに相談する。

## レビューのルール

### PR を出す人

- PR 作成時に Reviewers を 1 人以上指定する（迷ったら Discord で依頼する）
- 反応がなければ、Discord で催促したり、別の人に頼み直したりしてよい
- 指摘を受けたら、対応して push し、コメントに返信したうえで、PR 画面の Reviewers 横の 🔄（**Re-request review**）を押して再レビューを依頼する
- Approve をもらった後に追加で変更を push した場合は、レビュアーに一声かける（追加の push では Approve は取り消されないため）
- 承認をもらったら、**PR を出した本人がマージする**

### レビューする人

- 依頼に気づいたら、なるべく早く見る
- すぐに見られないときは、黙って放置せず Discord で一言伝える（「明日見ます」「他の人お願い」など）
- 見るポイント
  - Issue の完了条件を満たしているか
  - 手元で動かして、動作に問題がないか
  - ブランチ名・コミットメッセージがルールに沿っているか
  - パスワードや API キーなどが含まれていないか
- 結果は以下のどれかで返す
  - **Approve**：問題なし
  - **Request changes**：直さないとマージできない点がある
  - **Comment**：質問や提案だけ（マージは止めない）

## Draft PR

- 作業途中でも、相談したいときや進み具合を見せたいときは **Draft PR** を出してよい（PR 作成画面の「Create pull request」横の ▼ から「Create draft pull request」を選ぶ）
- 完成したら「Ready for review」を押して、Reviewers を指定する
