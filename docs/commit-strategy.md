# コミット戦略

このドキュメントでは、コミットメッセージの書き方とコミットの切り方を定義する。
後から履歴を見たときに「いつ・何を・なぜ変えたか」がわかるようにすることが目的。

[Conventional Commits](https://www.conventionalcommits.org/ja/v1.0.0/) をベースにする。絵文字は付けない。

## 基本フォーマット

```
<type>[(scope)]: <説明> [#Issue番号]

[本文（任意）]
```

## type 一覧

| type | 用途 |
|---|---|
| `feat` | 新機能の追加 |
| `fix` | バグ修正 |
| `change` | 既存機能の仕様変更 |
| `refactor` | 動作を変えないコード整理（フォーマット修正を含む） |
| `docs` | ドキュメントのみの変更 |
| `test` | テストの追加・修正 |
| `chore` | 設定・ツール・依存関係・CI などの雑務 |

### `feat` / `change` / `fix` / `refactor` の見分け方

| 状況 | type |
|---|---|
| 今までなかった機能ができた | `feat` |
| すでにある機能の仕様・見た目・動きを **意図して** 変えた | `change` |
| 本来の仕様どおりに動いていなかったのを直した | `fix` |
| 動きは何も変わらず、コードだけ整理した | `refactor` |

## ルール

- `type` と `scope` は英語、`説明` と `本文` は **日本語** で書く
- `説明` は「〜を追加」「〜を修正」のように **体言止め** で簡潔に書く
- 1 行目は 50 文字程度以内を目安にする
- Issue がある場合は 1 行目の末尾に `#Issue番号` を付ける
- scope は変更範囲を括弧で示す（任意）。ブランチと同じ[スコープ一覧](branch-strategy.md#スコープ)を使う。例: `fix(backend): DB 接続のタイムアウトを修正 #34`
- 本文には「何を」ではなく「なぜ」変更したかを書く（[説明と本文の使い分け](#説明と本文の使い分け)を参照）
- `git config user.email` は GitHub に登録したメールアドレスと同じにする（違うと、コミットが自分のものとして GitHub に表示されない）
- Git / GitHub が自動で作るメッセージは規約の対象外とし、そのまま使う
  - `Merge pull request #1 from ...`（PR のマージ時）
  - `Revert "..."`（`git revert` 時）

## 例

| パターン | 例 |
|---|---|
| スコープあり・Issue あり | `feat(frontend): ログインフォームを追加 #12` |
| 同じ Issue の別の種類の変更 | `test(backend): ログイン API のテストを追加 #12` |
| スコープなし・Issue あり | `chore: ESLint を導入 #15` |
| スコープなし・Issue なし | `docs: README の typo を修正` |

本文を付ける場合の例は「[本文を書くとき](#本文を書くとき)」を参照。

## 説明と本文の使い分け

| | 説明（1 行目） | 本文（3 行目以降） |
|---|---|---|
| 書くこと | **何を** 変えたか | **なぜ** 変えたか |
| 必須か | 必須 | 任意 |
| 長さ | 50 文字程度まで | 自由 |

- 1 行目と本文の間には、必ず空行を 1 行入れる（Git は空行で 1 行目と本文を区別するため）

### 本文を書くとき

**コードを見ただけでは理由がわからないとき** に書く。次のどれかに当てはまったら書く。

- 他の方法もあったのに、この方法を選んだ
- 数値や設定値を決めた
- 仕様を変えた（`change`）
- 一見おかしく見えるが、わざとそうしている

```
fix(backend): DB 接続のタイムアウトを 30 秒に延長 #34

無料プランの DB はアクセスがない間スリープし、
起動に 10 秒以上かかって接続エラーになっていたため。
```

```
change(frontend): ログイン後の遷移先をマイページからホームに変更 #41

ユーザーテストで「ログイン後に何をすればいいかわからない」という
意見が多かったため。
```

1 行目だけで伝わるなら、本文は書かなくてよい（例: `docs: README の typo を修正`）。

### 本文の書き方（操作）

- **VS Code**：ソース管理のメッセージ欄で、1 行目を書いたら改行して空行を入れ、続けて本文を書く
- **コマンド**：`git commit -m "1行目" -m "本文"` のように `-m` を 2 回使うと、間に空行が自動で入る。`git commit`（`-m` なし）でエディタを開いて書くこともできる

## コミットの粒度

**後から見て、それ単独で意味がわかる単位** でコミットする。
「このコミットだけ取り消したら、何が元に戻る？」に一言で答えられるかが目安。

- 大きすぎる例：`feat: ログイン機能を作成`（画面・API・テストが全部入りで、一言で説明できない）
- 小さすぎる例：`修正`、`ボタンの色を修正` が 3 つ続く（単独では意味がわからない）
- 種類（type）が違う変更や、作業中に気づいた関係ない修正（typo など）は、別のコミットにする

## コミットしてはいけないもの

このリポジトリは **Public**（誰でも見られる）。一度 push したものは、後で消しても履歴に残る。

- `.env` ファイル、パスワード、API キー、トークンなどの秘密情報
- 個人情報
- `node_modules` などの自動生成されるファイル（[`.gitignore`](../.gitignore) で除外する）

秘密情報を push してしまったら、すぐに Discord で報告し、そのキーを無効化（再発行）する（ファイルを消すだけでは履歴に残るため不十分）。
